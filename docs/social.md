# 社交模块设计（ 版）

## 一、设计背景与目标

### 背景

本项目为  比赛作品，核心玩法是「一句话生成词灵 + AI 对战」。现有版本为纯单机体验，缺少社交互动，无法体现多人协作与 AI 角色陪伴的差异化价值。

### 设计目标

- 用**最小开发量**实现多人社交体验
- 聚焦**演示效果**，功能少而精
- 以「群聊 + 词灵陪伴 + 实时对战」为核心记忆点
- 不做广场、不做好友系统、不做注册登录

### 核心原则

> 能一个链接解决的，绝不做账号体系；能在房间里完成的，绝不做全局功能。

---

## 二、整体社交形态

### 2.1 形态定位

**「房间制社交」** —— 以房间为单位的临时私密空间，替代传统的广场/好友体系。

- 没有全局广场，没有好友列表，没有账号系统
- 玩家通过**房间码 / 分享链接**进入同一个空间
- 一个房间 = 一群玩家 + 他们各自的词灵 + 聊天 + 约战

### 2.2 用户旅程

```
生成词灵 → 创建房间 → 分享链接给朋友 → 朋友加入（带自己的词灵）
   → 群里闲聊 + @词灵互动 → 约战 → 实时对战 → 返回群聊复盘
```

## 三、功能模块设计

### 3.1 房间系统

#### 功能描述

- 玩家创建房间，获得 6 位房间码和分享链接
- 通过链接 / 房间码邀请朋友加入
- 房间内玩家上限：建议 4-6 人（ 演示 2 人即可）
- 房间为临时态，所有人离开后自动销毁（内存回收）

#### 房间内信息

- 房间码（6位，如 `K7X2P9`）
- 玩家列表（昵称 + 头像色 + 携带的词灵）
- 当前状态：闲聊中 / 对战中
- 聊天消息历史（最近 50 条）

#### 玩家身份

- 首次进入游戏自动生成临时身份
- 身份 = 随机 UUID（存 localStorage）+ 玩家昵称 + 头像色
- 不需要密码、邮箱、手机号
- 换设备数据丢失（ 阶段可接受）

---

### 3.2 群聊 + 词灵陪伴

> 这是最大的创意亮点——"AI 角色陪你们一起聊天"。

#### 核心体验

- 每个玩家可以**携带一个词灵**进入房间
- 玩家之间正常聊天
- 玩家可以 **@ 词灵** 提问，词灵基于自身 persona 回复
- 词灵之间会**低频自发互动**（性格碰撞冒泡）
- 词灵纯陪伴定位，不介入游戏功能

#### 词灵 Persona 来源

直接复用现有数据结构：

- `character.name` — 名字
- `character.spiritProfile.archetype` — 原型/性格
- `character.spiritProfile.catchphrases` — 语录 / 口头禅
- 角色技能、属性、稀有度 — 身份背书

> 现有单聊接口 `requestSpiritChat`（[spiritChat.ts](../src/utils/spiritChat.ts)）可复用，需改造为群聊场景的 prompt。

#### @ 词灵交互流程

```
玩家输入：@孙悟空 你觉得唐三打得过你吗？
  → 前端识别 @ 目标（词灵 rosterId）
  → 后端拼接群聊上下文 + 该词灵 persona
  → LLM 生成回复
  → 以词灵身份发回群聊
```

#### 词灵自发互动（冒泡）

- **触发条件**：群聊有新消息时，按一定概率（如 15%）触发在场词灵反应
- **反应形式**：一句话附和 / 吐槽 / 提问 / 表情
- **节流控制**：
  - 同一个词灵两次冒泡间隔 ≥ 30 秒
  - 同一轮对话最多 2 个词灵冒泡
  - 防止刷屏、控制 LLM 成本
- **词灵互撩**：两个词灵可以一来一回聊 1-2 轮后停下（概率触发，不保证）

#### 群聊消息类型

| 类型      | 发送者 | 说明                      |
| --------- | ------ | ------------------------- |
| 普通消息  | 玩家   | 正常文本                  |
| @词灵消息 | 玩家   | 触发对应词灵回复          |
| 词灵回复  | 词灵   | LLM 生成的 persona 化回复 |
| 系统消息  | 系统   | 加入/离开房间、约战邀请等 |
| 对战播报  | 系统   | 对战结果、精彩镜头        |

---

### 3.3 实时 1v1 对战

#### 入口

- 群聊中玩家 A 向玩家 B 发起约战（@对方 + 约战按钮）
- 对方接受 → 双方进入对战界面
- 房间内其他人可选择观战（时间够再加）

#### 对战实现

- 基于现有 [battleEngine.ts](../src/utils/battleEngine.ts) 改造
- 双方操作通过实时通信同步
- 战斗逻辑在**服务端**运行（防作弊 + 状态一致）
- 两端只负责：
  - 发送玩家操作（技能选择）
  - 接收战斗状态并渲染动画

#### 对战流程

```
约战邀请 → 对方接受 → 进入对战准备 → 双方选技能 →
服务端结算 → 推送战斗帧 → 两边播放动画 → 战斗结束 → 返回群聊
```

#### 对战后回流

- 战斗结束后自动生成战报（胜负 + 伤害数据 + MVP 技能）
- 战报推送回群聊，引发讨论
- 词灵可以针对战斗结果发表感言（触发一次 persona 化回复）

## 四、技术方案

### 4.1 架构总览

```
┌─────────────┐    实时消息     ┌─────────────────┐
│  前端 (Vite) │ ◄────────────► │  Pusher (实时层) │
└──────┬──────┘                 └────────┬────────┘
       │ API 调用                        │
       ▼                                 ▼
┌──────────────┐                 ┌─────────────────┐
│  Vercel API  │                 │  房间服务 (Node) │
│ (无状态函数) │                 │  (内存存房间)    │
└──────────────┘                 └─────────────────┘
                                          │
                                          ▼
                                   ┌──────────────┐
                                   │   LLM API    │
                                   │ (词灵聊天)    │
                                   └──────────────┘
```

### 4.2 技术选型

| 模块             | 选型                  | 理由                                   |
| ---------------- | --------------------- | -------------------------------------- |
| 前端             | React + Vite（现有）  | 复用现有代码                           |
| 部署（前端+API） | Vercel Hobby          | 免费、一键部署                         |
| 实时通信         | Pusher 免费版         | 20 万条/天、100 并发、接入快           |
| 房间状态         | 内存（Node 服务）     |  不需要持久化，重启丢了没关系 |
| 词灵 LLM         | 复用现有 AI 配置      | 已有 spirit-chat 接口，改 prompt 即可  |
| 战斗逻辑         | 复用现有 battleEngine | 搬到服务端运行                         |

> **备选方案**：如果不想多接 Pusher，可以用 PartyKit 或直接部署完整 Node 服务到 Render 免费层。

### 4.3 Pusher 免费版额度评估

- 每日消息量：200,000 条/天 ✅ 演示远远够
- 并发连接：100 个 ✅ 演示用几个人
- 每个频道无上限 ✅

完全满足  演示需求。

### 4.4 核心数据结构

#### 房间（Room）

```typescript
interface Room {
  roomCode: string; // 6位房间码
  players: Player[]; // 玩家列表
  messages: ChatMessage[]; // 聊天记录（最近50条）
  battle: BattleState | null; // 当前对战状态（无对战则null）
  createdAt: number;
}
```

#### 玩家（Player）

```typescript
interface Player {
  playerId: string; // 临时UUID
  nickname: string; // 昵称
  avatarColor: string; // 头像主题色
  activeSpirit: RosterCharacter | null; // 当前携带的词灵
  isOnline: boolean;
}
```

#### 聊天消息（ChatMessage）

```typescript
interface ChatMessage {
  id: string;
  type: "player" | "spirit" | "system" | "battle_report";
  senderId: string; // 玩家ID 或 词灵rosterId
  senderName: string;
  content: string;
  timestamp: number;
  spiritRosterId?: string; // 词灵消息附带
  mentions?: string[]; // @ 的目标ID列表
}
```

### P0 — 必须做（演示闭环）

| 功能                 | 预估工作量 | 说明                                      |
| -------------------- | ---------- | ----------------------------------------- |
| 房间创建 / 加入      | 半天       | 6位房间码 + 分享链接 + 玩家列表           |
| 实时群聊（玩家之间） | 半天       | Pusher 接入 + 消息收发 + 列表渲染         |
| @ 词灵回复           | 1 天       | 改造 spirit-chat 为群聊场景 + 前端 @ 交互 |
| 实时 1v1 对战        | 1.5 天     | 战斗引擎搬到服务端 + 状态同步 + 前端渲染  |
| 玩家临时身份         | 2 小时     | UUID + 昵称 + 头像色                      |

**P0 合计：约 4 天**

### P1 — 时间够再加（加分项）

| 功能           | 预估工作量 | 说明                        |
| -------------- | ---------- | --------------------------- |
| 词灵自发冒泡   | 半天       | 概率触发 + 节流控制         |
| 词灵互撩       | 半天       | 两个词灵一来一回            |
| 对战后词灵感言 | 2 小时     | 战斗结果触发 persona 化回复 |
| 观战模式       | 1 天       | 第三人进房间看对战          |

### P2 — 坚决不做（省时间）

- ❌ 好友系统 / 好友列表
- ❌ 注册登录 / 账号密码
- ❌ 排行榜 / 段位 / 积分
- ❌ 公会 / 小队 / 社群
- ❌ 广场 / 动态流 / 推荐
- ❌ 角色养成 / 装备 / 抽卡
- ❌ 跨设备数据同步
- ❌ 举报 / moderation

## 六、演示脚本建议

>  演示只有 3-5 分钟，节奏至关重要。

### 时间分配

| 环节              | 时长 | 重点                                         |
| ----------------- | ---- | -------------------------------------------- |
| 开场：词灵生成    | 30s  | 一句话 → 魔法阵 → 精美卡片（视觉冲击）       |
| 亮点：群聊 + 词灵 | 1min | 两人各带词灵，@互动 + 词灵互撩（提前调好梗） |
| 高潮：实时对战    | 1min | 从群聊约战 → 实时对打 → 战报回流             |
| 收尾：愿景        | 30s  | 一句话总结 + 未来想象                        |

### 演示技巧

1. **提前调试好词灵回复**：准备几个固定问题，确保词灵回复有梗、有反差感
2. **两个人配合**：一个人主控讲解，另一个人扮演朋友加入房间，节奏更自然
3. **用手机演示**：比用两个浏览器窗口更有说服力（真实场景）
4. **准备备用录屏**：万一现场网络/服务出问题，直接放录屏

## 七、风险与应对

| 风险                | 影响               | 应对                                |
| ------------------- | ------------------ | ----------------------------------- |
| LLM 响应慢 / 不稳定 | 群聊卡顿、演示冷场 | 提前缓存几个演示用的回复兜底        |
| Pusher 连接失败     | 实时功能挂掉       | 准备录屏备用                        |
| 对战不同步          | 体验差             | 以服务端状态为准，客户端做插值补间  |
| 词灵刷屏 / 人设崩   | 观感差             | 严格节流 + 强 persona 约束 prompt   |
| 开发量超时          | 做不完             | 严格按优先级砍，先跑通 P0 再考虑 P1 |
